**十六个易踩坑**

1. **欢迎页不要再改**，版式/字号/配色/文案/时序都不动，要调也先问。
2. **首页与酒单都不用八公明朝**：字体子集只含欢迎页 43 个字；想让酒单也用，必须另建子集（新脚本 + 新 wxss），不要直接 `@import` 现有那份。
3. **改 `utils/mock-data/` 的分类或商品，必须递增 `config/index.js` 的 `seedVersion`**，否则本地 storage 缓存不更新（`services/{categories,products}.js` 按版本自动重播种）。**桌号表用独立的 `tableSeedVersion`**（`utils/mock-data/tables.js` 改完递增它）。
4. **商品字段已统一**：`id / name / category / price / description / image / isAvailable`，分类 id 固定为 `traditional / signature / non_alcoholic / snacks`。不要再引入 `categoryId / desc / status`（services 里只为后台兼容保留了入参别名）。
5. **玫瑰组件与素材仍在仓库但已排除出包、无人引用**（`rose-stage` / `petal-field` / `petal-layer`、`assets/rose`、`assets/petals`）。用户放弃了玫瑰效果，**没让删文件**。
6. **首页不展示到店信息**（地址/营业/电话/地图已按用户要求移除），别再补回去。门店信息仍是「（待填写）」。
7. **订单状态只有 4 个**：`pending(待接单) → making(制作中) → completed(已完成)`，`cancelled(已取消)`。用户已确认**去掉「待取餐」**，别再加回来；旧的 `accepted/ready` 会在读取时自动迁移。
8. **桌号不得生成或手动选择**：顾客端只来自扫码参数/本地存储；缺失时订单确认页必须拦截并提示重新扫码。桌号与商品快照、金额都不许前端随意拼。**开发版**在「开发自检 → 当前桌号（调试）」提供了等价于扫码的桌号选择（`app.setTable` 同一套校验，`envVersion` 门控），用于没有真实二维码时调试；正式版不显示，也不要把它做成手动选桌。
9. **首页是自定义导航**（`navigationStyle: custom`）：右上角「我的」必须按 `wx.getMenuButtonBoundingClientRect()` 放到胶囊下方（`profileTop`），否则会压在微信原生胶囊的「关闭/退出」按钮下面，点击直接退出小程序。改顶部布局时保留这段逻辑。
10. **管理端入口不是权限**：入口在「我的」页常驻，但真正的拦截是 `utils/admin-guard.js → authService.requireOwner()`（5 个管理页进页都调）。不要靠 `wx:if` 隐藏按钮当鉴权；正式版必须云函数校验。
11. **管理页切页用 `wx.redirectTo`**（`admin-nav`），栈深保持 1 层；原生 tabBar 固定 4 个，**不要给管理端加第 5 个 Tab**。
12. **商品图片只读**：老板端禁止出现 `wx.chooseMedia / chooseImage`，也不许把 `wxfile://` 临时路径写进 `image`。图片由维护者统一写字段，`services/media.js` 只是预留契约（当前返回 4030）。
13. **老板取消订单必须带原因**（服务层 4011），顾客取消仍 `by:'customer'` 免原因；改这条要同步 `verify_stage5.js` 的取消断言。
14. **价格输入是「元」、存储是「分」**：表单必须走 `utils/format.yuanToFen()`（字符串解析），不要 `parseFloat * 100`。
15. **调酒师端只处理订单**：不能取消、不能处理异常、不能改商品/价格、不展示订单金额与营业额；异常只能提交给老板。改权限要同步 `auth.can()`、服务层拦截与 `verify_stage7`。
16. **轮询不是实时推送**：工作台必须常驻「模拟实时」标注；M4 换 `services/order-feed.js` 为云端订阅，不要把本地定时刷新写成「实时」。

## 4. 硬约束

1. 技术栈固定微信原生，不引入 Taro / uni-app / 第三方 UI 库。
2. 不擅自重构或删除已完成模块；动 M0 页面先说明原因与影响。
3. 先说明改哪些文件、为什么，得到批准再写代码；交付后等用户验收，不自行判定通过。
4. 视觉：不加 Logo/印章/水印；全站仅商品详情底部面板允许一层阴影；**全站仅欢迎页有动效**（纯 opacity 淡入）；不做双列卡货架、不做眉标、不做全大写小标签（品牌英文除外）、不加箭头。
5. 示例数据一律标注「示例」，商品名用「示例·」前缀，不虚构门店信息；图片为空时用 CSS 酒标式占位块，有图自动显示，不伪造产品照。
6. 金额以「分」存储计算，展示转元。
7. 正式版管理员鉴权、订单金额、订单状态必须服务端校验；演示阶段不得伪装真实支付。
8. **底部导航固定 4 个 Tab：首页 / 酒单 / 购物车 / 我的订单**。`我的` 不能再做第 5 个 Tab，只能从首页右上角进；`我的订单` Tab 与 `我的` 页里的订单入口指向同一页面。
9. 原始字体 `HakkouMincho-v1.004/HakkouMincho.ttf` 与用户素材**逐字节不要改**；`styles/font-hakkou.wxss` 是生成文件，不要手改。
10. 酒单分类与搜索都走 `services/products.listProducts({ category, keyword })`，页面不重复过滤逻辑；M4 换云函数只改 services。
11. **订单金额只由 `services/orders.createOrder` 按商品表核算**，页面传来的金额一律不采信；订单条目是下单时快照，后续改商品价格/名称不影响历史订单。
12. **订单状态只能走 `updateOrderStatus` / `cancelOrder`**，页面不得直接改 storage；顾客只在待接单可取消，制作中及之后由店员（M3）处理。
13. **「模拟推进」按钮仅演示用**，必须常驻「演示」字样；M3 建后台后替换为真实店员操作，不得伪装成商家已处理。
14. **管理端只能经 `services/*` 读写**：管理页不得直接引 `utils/storage` 或 `setStorageSync`（`verify_stage6` 会查）；订单/商品只有一份数据，禁止各页面自存副本。
15. **订单异常是旁挂字段**（`order.exception`），不要再加第五个订单状态；三端状态枚举必须一致。
16. **管理端配色/结构沿用 `styles/admin.wxss`**：细线分隔、不用卡片阴影、不加动效；顾客端页面样式不要为此改动。
17. **状态机仍只有 4 态**：`待接单 → 制作中 → 已完成` + `已取消`；用户已再次确认**不加「待取餐」**，调酒师「制作完成」即完成。
18. **调酒师会话独立**（`lm_bartender_session`），与老板 `lm_admin_session` 分开；演示口令 `1234` 只放 `config/index.js`，页面不得写死；正式版权限必须云函数校验。
