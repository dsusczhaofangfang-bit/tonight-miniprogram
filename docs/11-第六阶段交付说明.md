## 1. 本阶段做了什么

1. **老板入口与 Mock 登录**：「我的」页新增「老板管理后台」（未登录显示「需口令」），点击进 `admin-login`，口令页常驻「演示鉴权」，成功后进概览；已登录则直接进后台，「我的」页出现「退出管理后台」。
2. **页面级守卫**：5 个管理页进页统一走 `utils/admin-guard.js → authService.requireOwner()`，未登录立即重定向登录页，且不加载任何订单/商品数据。入口只是体验，守卫才是拦截。
3. **角色模型**：`authService` 由「只有一个 admin」改为 `ROLES = customer / owner / bartender`，会话 `{ role:'owner', mock:true }`；第五阶段的 `role:'admin'` 会话读取时自动归一为 `owner`，老数据不失效。调酒师角色调用登录会被明确拒绝（4031），为后续工作台留位。
4. **经营概览**：今日订单数、今日营业额、待处理订单、在售商品数四个指标 + 待处理异常提示 + 最近 5 笔订单。口径固定「已取消不计入订单数与营业额」；数据实时读 orders / products，不另存副本，进页刷新、下拉刷新、每次操作后刷新。
5. **订单管理**：全部 + 四个状态筛选（带各状态计数）、订单卡（编号/状态/桌号/时间/摘要/件数/金额/异常标记）、详情页（编号、桌号、下单与更新时间、商品名称/单价/数量/小计、备注、总额、状态时间线）。
6. **订单处理**：老板可「确认接单」（待接单→制作中）、「完成制作」（制作中→已完成）；可在待接单/制作中取消，**必须填写取消原因**；已完成/已取消为终态。
7. **异常处理**：新增旁挂字段 `exception = { status, reason, note, by, createdAt, resolvedAt, resolvedBy, resolution }`，老板可标记异常（缺货/无法制作/顾客要求/其他 + 说明）与解除异常，全部写入 `statusLogs`。**异常不新增订单状态**，三端枚举仍是四个。
8. **商品管理**：列表（分类筛选、名称搜索、上下架状态、在售/下架计数）、新增、编辑（名称/英文名/分类/价格/介绍/上下架）、一键上下架。价格在表单按「元」输入，服务层存整数分；商品无图沿用 CSS 酒标式占位块。
9. **商品图片改为只读**：按你的要求，管理端**不提供任何上传/相册选择/更换图片**的入口，只做只读预览并注明「图片由系统维护人员统一更新」；`services/media.js` 预留维护者接口（当前明确返回未开放）。

## 4. 权限：Mock 与正式权限的边界

| 层次 | 现在的做法 | 正式版要做的事 |
| --- | --- | --- |
| 入口 | 「我的」页常驻入口，未登录显示「需口令」 | 入口可以保留，但必须服务端校验 |
| 会话 | `lm_admin_session`，`{ role:'owner', mock:true }`，口令 `8888` 写在客户端 | 云函数登录，签发会话/token，openid 白名单 + 角色 |
| 页面 | `requireOwner()` 守卫，未登录重定向 | 每个管理接口在云函数里再校验一次，不信任前端 |
| 数据 | 本地 storage 全量可读 | 数据库权限规则：只有管理员可写 orders/products |

> 结论要写在明面上：**前端隐藏入口、前端口令都不构成安全边界**。本阶段只是把 Mock 流程跑通并把权限结构留好（`ROLES`、`requireRole`、`by: 'owner'` 时间线），正式版不能只靠这一层。

## 5. 数据管理方式

- **单一数据源**：订单仍是 `lm_orders`、商品仍是 `lm_products`，管理页**不写 storage、不建副本**，全部经 `services/*`；`verify_stage6` 会静态检查管理页里没有 `utils/storage` 与 `setStorageSync`。
- **同步机制**：顾客端页面在 `onShow` 重新读服务层；管理端订单列表/商品列表同样在 `onShow` 重读，所以在任一端口改动后，切回另一页即可看到最新值。当前**没有推送/轮询**（那是调酒师工作台与 CloudBase 阶段的事），文档里不写成「实时」。
- **金额**：一律整数分。表单输入元 → `yuanToFen()` 字符串解析（`58.5 → 5850`、`58.05 → 5805`），拒绝 `abc / -1 / 1.234`；展示用 `fenToYuan()`。`verify_stage6` 断言所有订单与商品金额都是整数。
- **价格快照**：订单条目在下单时写死名称/单价/小计/分类/图片，改商品价不影响历史订单（脚本覆盖）。
- **上下架**：`products.isAvailable` 是唯一开关。下架后酒单不返回、详情显示已下架、加购返回 4040、下单返回 4004、购物车里已存在的条目自动剔除；重新上架即恢复。
- **图片**：`image` 字段保留。有值显示图片，空值回落酒标占位块。管理端只读，不写入任何 `wxfile://` 临时路径；`services/media.js` 只声明维护者接口契约（`MAX_IMAGE_BYTES = 300KB`、允许 jpeg/png/webp），调用返回 4030。

## 6. 状态机与异常

```text
pending(待接单) ──► making(制作中) ──► completed(已完成)
      │                  │
      └──────────────────┴──► cancelled(已取消)

规则：只能前进；顾客仅 pending 可取消；老板可在 pending/making 取消且必须填原因；
      completed / cancelled 为终态；每次变更写 statusLogs（by: customer | owner | demo | system）。
```

- 本期**没有「待取餐」**：按你的最新指示「两者的待取餐都去除」，顾客端与老板端统一保持四态，`utils/constants.js` 与顾客端筛选、详情时间线零改动。
- 异常是旁挂标记，不是状态；标记/解除都写时间线并注明操作人与原因，列表与概览用 `openExceptions` 计数提示。

前置：微信开发者工具导入 `仓库根目录` → 编译。演示口令 `8888`。若要先造订单：用「开发自检 → 当前桌号（调试）」设桌号 → 酒单加购 → 结算下单。

2. **普通顾客无法进入**：未登录时点入口 → 落在口令页；输错口令提示「口令错误」且不写入会话；直接改路由进 `pages/admin-overview/admin-overview` → 被重定向回登录页（可在开发者工具「编译模式」直接打开该页验证）。
3. **查看订单与详情**：订单管理页默认「全部」，四个状态计数与列表一致；点任一卡片 → 编号、桌号、下单时间、商品名称/单价/数量/小计、备注、总额、状态记录齐全。
4. **改状态后顾客端同步**：订单详情点「确认接单」→ 状态变「制作中」；切底部 Tab「我的订单」→ 筛选「制作中」→ 该订单在列表里，进详情时间线显示「制作中 · 老板」；再回后台点「完成制作」→ 顾客端变「已完成」。

7. **下架后不能买**：下架商品的详情页显示「已下架」且不可加购；若它已在购物车，进购物车会被自动剔除；用已勾选的其它商品结算正常。
8. **历史订单不受改价影响**：改某商品价格后，打开改价前下的订单 → 单价与总额仍是旧价。
9. **概览计算正确**：记下今日订单数与营业额 → 新下一单 → 回概览（`onShow` 刷新）数字增加；取消一单 → 数字回退且「已取消不计入」；下架一款商品 → 「在售商品」减 1。
10. **持久化**：完全关闭小程序再打开 → 后台登录态、改过的商品、订单状态都还在；「开发自检 → 重置演示数据」可恢复初始示例。
